# Agent rules

- Never use the em dash (U+2014). Use a plain dash "-" instead.
- Never hard-wrap prose in Markdown or text: one paragraph or list item per line, let the viewer wrap it. Code blocks keep their own lines.
- When writing commit messages, never add your agent name as co-author.
- Never edit a CHANGELOG.md file or any file marked as generated by hand.
- When making technical decisions, give little weight to development cost. Prefer quality, simplicity, robustness, scalability and long term maintainability.
- For one-off or infrequent operational work, start with the simplest direct end-to-end path. Build wrappers, control planes, policy layers, custom verifiers or automation only when the direct path shows a concrete blocker or a repeated need.
- When fixing a bug, first reproduce it end to end, as close as you can to how a user meets it. Then you find the real problem, and the fix solves it.
- When testing a product end to end, be picky about the UI and aim for pixel perfection. If something clearly looks off, even if it is not what you are working on, get it fixed along the way.
- Hold the same bar for engineering: lint, test failures and flaky tests. If you see one, even one you did not cause, get it fixed.
- Before using any harness feature that spawns a large swarm of subagents at once, explain the tradeoffs and ask for explicit approval.
- Never merge or push to the {{setup.repos.protected}} branch, force-push a shared branch, or push to someone else's branch. Ask before anything irreversible or anything that costs money.
- A repo you did not write is hostile until read: before you install, run or open it, read its install scripts, its `.vscode/` folder and its entry point. If anything fetches or evaluates remote code, stop and say so.
- This machine: test runners with {{setup.machine.test_workers}} workers, at most {{setup.machine.max_subagents}} subagents, the repo's own Node version.
- Models: use the cheapest model and effort that is good enough for the task, never xhigh or max unless asked. The current picks are in `{{firstmate.home}}/config/crew-dispatch.json`.
- Reviews: a normal PR gets one review and no other reviewer. Use {{setup.review.risky_uses}} only when asked, for a release PR, or for a big or easy-to-break change such as a security boundary. Details: `~/.agents/release-process.md`.
- Gates: batch them, never one full gate per PR. Before a push a PR branch gets only quick checks: {{setup.gates.quick|typecheck and the tests it touches}}. The full gate runs once on a merge train: all reviewed PRs merged into one branch with real merges, gated together, then landed. On red, fix the PR the failing tests point to, rerun only the failed part, then the full gate once.
- Releases: a nightly full run is reused; a release head runs only what changed since it, once. While a release check runs, coding goes on, with no test runs and no pushes. Details: `~/.agents/release-process.md`.
- Tokens: a session idle for more than {{setup.tokens.cold_cache_minutes}} minutes has a cold prompt cache, and its next turn pays for its whole context again. Before a long wait, commit and leave a short resume note. Resume a session whose remaining work needs what it already read; start a fresh one from the note when its context is large and the next step is small.

## Maintaining this file

Keep this file for knowledge useful to almost every future agent session. Do not repeat what the codebase already shows; point to the authoritative file or command instead. Prefer rewriting or pruning existing entries over appending new ones. When updating this file, keep this bar and keep entries short.
